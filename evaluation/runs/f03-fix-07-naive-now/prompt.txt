# Task: a `--now` without a UTC offset must not traceback

**Edit `scripts/status_page.py` and `tests/test_status_page.py`. Nothing else.**

A single bounded fix. Do not refactor, do not improve anything the task does not name, and do not
touch any other finding.

## Current behavior

`--now` is parsed with `type=datetime.fromisoformat` (`scripts/status_page.py:306`). That accepts
`2026-08-19T10:05:00` — a valid ISO-8601 string with **no offset** — and produces a naive
`datetime`. Every `started_at` on disk is offset-aware, so the subtraction in `collect_status`
(`duration = (now - started_dt).total_seconds()`) raises:

```
TypeError: can't subtract offset-naive and offset-aware datetimes
```

The `except (KeyError, ValueError)` around it does not catch `TypeError`, so the traceback reaches
the user. Reproduce it:

```
mkdir <ws>\r1
echo {"kind":"task","task_id":"x","title":"t","started_at":"2026-08-19T10:00:00+00:00"} > <ws>\r1\started.json
python scripts/status_page.py status --runs <ws> --now 2026-08-19T10:05:00
```

The previous fix (`f03-fix-02`) made an *unparseable* `--now` exit cleanly; this is the parseable
but naive case, which that fix did not cover.

## Desired behavior

A naive `--now` is treated as UTC. `--now 2026-08-19T10:05:00` behaves exactly like
`--now 2026-08-19T10:05:00+00:00`: same durations, exit 0, no traceback. An offset-aware `--now`
is unchanged.

## Out of scope

- Do not change how an unparseable `--now` is handled — `f03-fix-02` already covers it, keep its
  test passing unchanged.
- Do not change `collect_status`'s signature, the output schema, the server, or any other
  behaviour.
- Do not address any other review finding.
