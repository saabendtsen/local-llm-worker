# Review Task — test strength only

You are reviewing a code change **you did not write**. You have one narrow job.

**Your only subject: whether the tests would actually catch a bug.** Not whether they pass — they
do. Not whether there are enough of them. Whether they *discriminate*.

Ignore the implementation's style, naming, error handling and design. Another reviewer covers
those. If you find something outside your remit, drop it.

## The thing you are looking for

Tests written after the code tend to check that the code agrees with itself. They pass, they look
thorough, and they would keep passing if the implementation were wrong.

The test to distrust most is the one that reads as if the author ran the code, saw the output, and
wrote an assertion matching it.

## The method — this is the whole job

For each test, answer one question: **what could I change in the source that would NOT make this
test fail?**

If you can name such a change, and it would be a real bug, the test is weak. If you cannot name
one, the test is doing its job.

**Then actually do it.** Do not reason about it — make the change, run the test, and record what
happened. Restore the file afterwards.

Mutations worth trying, in rough order of value:

1. **Return a constant** from the function under test — the same shape, wrong values.
2. **Invert a condition** — swap `if x` for `if not x` in the changed code.
3. **Skip a step** — delete the line that filters, sorts, deduplicates, or validates.
4. **Swap two values** that should be distinguishable — two categories, two counts, two keys.
5. **Zero out a value** the test claims to check.
6. **Return an empty collection** where items were expected.

For each mutation: apply it, run only the relevant tests, record pass or fail, restore.

## What counts as a finding

- **A test that survives a mutation that is a real bug.** Name the mutation and paste the passing
  output. This is the strongest possible finding here.
- **An assertion that cannot fail.** `assertIn(k, d)` where the code inserts `k` unconditionally.
  `assertGreaterEqual(n, 0)` on a count. An assertion comparing a value to itself recomputed the
  same way.
- **A test whose name promises more than it checks** — "matches" or "equals" in the name, with no
  comparison in the body.
- **Behaviour the specification requires with no test at all.** Read the spec's list of required
  cases and check each one has a test that would fail without it. **The entry point — argument
  parsing, exit codes, stderr — is the usual gap.**
- **An assertion pinned to nothing external.** The value asserted should come from the
  specification, a known-good literal, or a source the code does not itself produce. If the
  expected value is computed the same way the code computes it, the test proves nothing.

## How to work

1. Read the specification's list of required cases.
2. Read the test file. For each test, write down the mutation you predict it will not catch.
3. Apply each mutation, run the tests, record the result, restore the source.
4. Report only mutations you actually ran.

**Restore every file you touched.** Confirm with `git status` before reporting, and say in your
output that you did.

## Report

Output only these blocks, nothing before or after.

```
### FINDING <n>
axis: test-strength
file: <test path>:<line-or-range>
severity: high | medium | low
confidence: verified | suspected
problem: <which test is weak, and in what way>
mutation: <the exact change you made to the source>
result: <what the tests did — "27 passed" is the damning outcome here>
why: <the real bug this mutation represents>
```

`severity: high` means the mutation is a genuine bug that ships silently.
`confidence: verified` requires a mutation you actually applied and ran. Without one it is
`suspected`, and you may report at most two suspected findings.

End with exactly one line:

```
SUMMARY: test-strength=<n> blocking=<n> mutations-run=<n> restored=<yes|no>
```

**An all-clear with `mutations-run=0` means you did not do the job.** Report the number honestly.

# Task: give the status page real detail — live progress, per-kind facts, pipeline grouping

**Edit `scripts/status_page.py`.** Then **edit `tests/test_status_page.py`**. Change no other file.

## Current behavior

`scripts/status_page.py` (f03) lists runs from `evaluation/runs/<id>/`: a run with `started.json`
and no terminal file is running; one with `run.json` / `review.json` / `triage.json` is finished.
The JSON has `current`, `running`, `recent` (capped at 10), `unreadable`, `ignored`; each run
record carries `kind`, `task_id`, `title`, `started_at`, `duration_seconds` and, when finished,
`finished_at`. The HTML shows a one-line "Current" and a four-column table. It is correct and bare.

What it cannot say: how far along the current run is, whether a finished task passed its
acceptance command, how big its diff was, how many findings a review produced, what a triage
decided, or which runs belong together. Tonight's `evaluation/runs/` holds an implement, four
reviews, a triage and eight fixes for `f03` side by side with the same shape for `f02`, and the
page shows them as one flat list.

Since today every `started.json` also carries `"pipeline"` — the first dash-separated token of
the spec id, so `f03-status-page`, `f03-fix-02-…`, the `rv3-*` reviews of it and `tr-f03-*` all
say `"pipeline": "f03"`. Older directories lack the key.

## Desired behavior

The same two commands, the same files, stdlib only, no JavaScript, inline CSS only. Everything
already in the JSON stays exactly as it is (existing tests must keep passing unchanged); the
following is **added**.

### 1. Live progress for running runs

Each entry in `running` (and therefore `current`) gains:

- `turns` — the number of lines in the run's `events.jsonl` whose JSON object has
  `"type": "turn_end"`; `tool_calls` — likewise for `"type": "tool_execution_end"`. Both `0` when
  the file does not exist yet.
- `last_activity_at` — the file's mtime as an ISO-8601 UTC timestamp, `null` when absent;
  `last_activity_seconds_ago` — `now − mtime`, rounded to one decimal, `null` when absent.

**Reading must be incremental.** `events.jsonl` for one run grows to hundreds of megabytes — both
harnesses re-emit the whole message on every token — and the page refreshes every ten seconds.
Keep a module-level cache keyed by path holding `(bytes_consumed, turns, tool_calls)`; on each
call read only from `bytes_consumed` to the current end, update the counts, store the new offset.
If the file is smaller than `bytes_consumed` (truncated, replaced), start over from zero. Count a
line only when it parses as a JSON object with the `type` key; skip malformed lines silently; a
partial last line (no trailing newline) must not be consumed until it is complete — leave the
offset before it.

### 2. Per-kind detail for finished runs

Each entry in `recent` gains `"detail"`, a dict whose content depends on `kind`:

| kind | source | keys |
| --- | --- | --- |
| `task` | `run.json` | `verify_passed` (bool, from `verify.passed`), `meaningful_pass` (bool), `files_changed`, `lines_added`, `lines_removed` (from `diff`), `turns` (from `events.turns`), `timed_out` (true if `worker.timed_out` or `worker.idle_timed_out`) |
| `review` | `review.json` + `review.md` | `turns` (from `events.turns`), `timed_out` (as above), `findings` — the number of lines in `review.md` that start with `### FINDING`, `0` if the file is missing |
| `triage` | `triage.json` | `valid` (bool), `attempts` (length of `attempts`), `tasks` (length of `tasks` or `0`), and `dispositions` — a dict counting `triage.dispositions[*].disposition` values, e.g. `{"fix": 3, "fix-test-only": 3, "defer": 2, "drop": 2}`; `{}` when `triage` is absent or `valid` is false |

Missing keys → `null` for that field, never an exception. `detail` is `{}` for an unknown kind.

### 3. Pipeline grouping

Each run record (running or finished) gains `"pipeline"` — the `started.json` value, or `null`.
The top level gains `"groups"`: a list, newest first by the newest `started_at` in the group, of

```json
{"pipeline": "f03" | null, "running": <n>, "finished": <n>, "runs": ["<task_id>", ...]}
```

with `runs` listing **every** run of that pipeline (not only the ten in `recent`), newest first.
Runs without a pipeline go in one group with `"pipeline": null`, last.

### 4. The page

`GET /` renders, top to bottom:

- a **status line** as the first element of `<body>`, and also as the `<title>`: `RUNNING: <title>`
  when something is in flight, else `IDLE — last run finished <finished_at of the newest finished run>`
  or `IDLE` when nothing has ever run;
- the **current run** panel: title, kind, id, pipeline, elapsed, turns, tool calls, and
  "last activity Ns ago";
- one **section per group**, headed by the pipeline name and its running/finished counts, with a
  table: ID, kind, title, state, started (local time is fine, say so in the summary), duration,
  and a detail column rendered from `detail` — for tasks `✓`/`✗` plus `+added/−removed`, for
  reviews `<n> findings`, for triages `fix <n> · test <n> · defer <n> · drop <n>`;
- durations as `m:ss` under an hour and `h:mm:ss` from an hour up (`3600.0` → `1:00:00`,
  `59.0` → `0:59`);
- a `<style>` block with a `@media (max-width: 600px)` rule that lets tables scroll horizontally
  (`overflow-x: auto` on a wrapper) and drops the margin — the page is read from a phone.

Every value reaching the page still passes through `html.escape`.
